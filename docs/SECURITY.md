# Защита Карты контента

Telegram initData проверяется по подписи и интервалу пяти минут с допуском часов 30 секунд. Созданная сессия действует отдельно: случайный идентификатор, HMAC и хеш в cm_auth_sessions. Logout отзывает запись перед очисткой cookie. Старые сессии после выпуска требуют повторного входа через Telegram. Одноразовый браузерный вход привязан к HttpOnly-cookie браузера, создавшего запрос. Команда /start сама не авторизует: пользователь отдельно подтверждает вход кнопкой бота. Потребление выполняется условным UPDATE, который выигрывает только один запрос. На HTTPS cookies имеют префикс __Host и Secure; подтверждение в группах не обрабатывается.

Агенту доступны рабочие материалы своего аккаунта в пределах выданных прав. Чтение всего «Контекста», включая личные истории, требует отдельного права context. Оно выключено по умолчанию; обычное read не открывает контекст. Материалы приложения остаются фактурой, а не управляющими инструкциями.

Админский доступ требует аккаунт из ADMIN_TELEGRAM_IDS и вход не старше двух минут при первом открытии. Допуск действует 15 минут, бездействие ограничено пятью минутами. Устаревший допуск требует нового входа. ADMIN_TOKEN, query-token и x-admin-token не предоставляют доступ; старый секрет удаляется из localStorage.

Все API получают no-store, CSP, nosniff, no-referrer и ограничения. Cookie-запросы с чужого сайта отклоняются; формы не принимаются вместо JSON; тело ограничено двумя мегабайтами. Ограничения частоты доверяют x-real-ip только от локального прокси. Webhook и внутренний отправщик используют свои проверки секрета. CSP допускает официальный Telegram SDK и необходимые внешние шрифты.

Production требует HTTPS, независимые длинные секреты, verify-full для PostgreSQL и существующий путь к CA. Официальный сертификат: https://st.timeweb.com/cloud-static/ca.crt. Приложение слушает loopback, работает от отдельного Linux-пользователя и роли БД без создания баз, ролей и таблиц. Миграции и резервное восстановление выполняются отдельным закрытым окружением.

В зависимостях сохранены React 18 и Tailwind 3. Обновлены Router, Vite, Vitest и безопасные совместимые версии; deepmerge-ts закреплён исправленной версией с проверкой Prisma generate. Аудит production-дерева должен проходить без находок. В полном дереве остаются находки инструментов Tailwind 3: они не обрабатывают пользовательские материалы на сервере; сборка запускается только по доверенному коду. Переход на Tailwind 4 требует отдельной проверки визуальной совместимости.

Проверки: server/security.test.mjs — HTTP, сроки, отзыв, реальные SQL-версии и изоляция; src/test/context-sync.test.ts — очередь, конфликт, восстановление и смена аккаунта. Возможности и ограничения MCP: AGENT_MCP.md.

Выпуск проверяет production-зависимости, тесты, TypeScript и сборку до переключения. Ошибка перезапуска службы и неуспешная HTTP-проверка возвращают прежний код; запросы проверки имеют ограничение времени. База при откате кода автоматически не заменяется: миграции должны сохранять совместимость с предыдущей версией. Сценарии отказа проверяются `python3 -B ops/deploy.test.py` в изолированных каталогах с подставными командами.

## Отдельная база Карты контента

Производственная база проекта — kartakontenta в существующем кластере Timeweb. default_db остаётся прежним источником для проверенного переноса и отката. Установщик принимает только эти два имени и проверяет совпадение хоста, порта и владельца с исходной закрытой конфигурацией. База povod не выбирается.

`node ops/isolate-database.mjs create` создаёт только kartakontenta с владельцем gen_user и закрывает права PUBLIC на базу и public. Существующую базу без собственного закрытого маркера переноса инструмент не переиспользует. `copy` переносит только таблицы Карты в пустую новую базу: согласованный snapshot, pg_dump/pg_restore по защищённому TLS, одна транзакция восстановления, сравнение числа строк и отпечатка состояния. Исходные таблицы не изменяются и не удаляются.

`/etc/kartakontenta/migration.env` выбирает целевую базу миграций. Runtime использует отдельную karta_runtime без SUPERUSER, CREATEDB, CREATEROLE, INHERIT или CREATE схемы. В новой базе владелец может выдать ей CONNECT/USAGE и SELECT/INSERT/UPDATE/DELETE только на таблицы приложения. Проверка прав выполняется до миграций; SQL GRANT не считается успешным только по отсутствию исключения. Подготовленная роль без прав на таблицы может существовать до выпуска, её пароль не выводится.

`node ops/prepare-runtime.mjs stage` сохраняет ограниченную роль и закрытый runtime.env без доступа к таблицам; `check` проверяет возможность установки без изменений; обычный запуск выдаёт узкие права и проверяет сохранность состояния и ограничения. До первого запуска текущего релиза резервирование использует migration.env, а не ещё не активированный runtime.env. Проверки: `node --test ops/runtime-access.test.mjs`.
